## 実装と実行境界

`kronello-jobs` は作品外の状態 DB / 固定入力 / FIFO lease / heartbeat / cancel / prune / detached spawn を担当する。`kronello-service` が RenderSnapshot の作成と実行を共有し、CLI / MCP は共通 worker 入口を使う。API は `render.submit` / `job.get` / `job.list` / `job.cancel` / `job.prune`、公開 registry は24操作。詳細は [ADR-0050](../adr/0050-fixed-job-execution-and-publication.md)。

画像連番は RGBA16F / PNG / JSON、MOV は同梱 LGPL runtime の ProRes + stereo 48 kHz PCM24。MOV の明示 clips と映像を同じ固定 envelope から出力する。backend はすべて明示 `cpu-reference`。GPU の不在時に暗黙 fallback する実装はない。

全 job test は `tempfile` と `KRONELLO_STATE_ROOT` / `JobConfig::at` を使う。CLI / MCP の実 binary を別プロセスとして起動し、投入元の終了後に状態 DB を別の呼出しから読む。実ユーザー状態 directory は開かない。当時の CLI process test の heartbeat 間隔は50 ms、期限は3000 ms、MCP は50 / 1000 ms（CLI の現行設定は末尾の CI heartbeat 修正節を参照）。production の既定は1000 / 30000 ms。待機や artifact corruption の注入は `test-job-control` と debug_assertions が両方有効な test build に限る。

## 追加の固定入力・失敗経路

- `fifo_one_slot_and_fixed_snapshot_survive_project_edits`: 投入後に project の fill color を変更しても、両 job の PNG が投入前の同期 CPU render と byte 一致。編集後の同期 render は異なる。job manifest の revision / snapshot hash は投入時点のまま。
- `worker_checks_saved_schema_semantics_features_and_input_hash`: queued 入力の envelope schema、snapshot 意味版、required_features を別々に変更して worker の互換性検証を確認する。互換性ケースは保存 envelope の byte hash もテスト側で更新し、単なる hash 失敗と区別する。byte hash を更新しない破損は JOB_INPUT_HASH_MISMATCH。
- `changed_asset_content_fails_worker_with_typed_error`: 先行 job で slot を占有し、queued job の素材を同じ byte 長で変更。worker が ASSET_HASH_MISMATCH で失敗し、final output を作らない。
- `worker_verifies_saved_font_lock_before_output`: 固定 FontRef に対し違う font bytes を渡し、worker 開始時の ASSET_HASH_MISMATCH を確認する。
- `cancel_running_and_queued_jobs_cleans_temporary_output`: 実 CLI job.cancel を running / queued の双方へ発行。両方が canceled、final output なし、temporary directory が残らない。
- `duplicate_worker_cannot_fail_or_steal_an_active_job`: 同じ ID の worker を再度実起動し、JOB_ALREADY_OWNED で拒否。元 PID と running を維持し、元 worker が成功する。
- `mov_export_uses_fixed_video_and_audio_snapshot`: 明示音声 clip を持つ実 job が ProRes / PCM24 MOV を確定し、映像・音声 report の RenderSnapshot hash、3 frame、2 stream を照合する。別形式の成功を MOV の代替として扱わない。
- `invalid_configuration_ids_and_newer_database_are_rejected`: 0 slot、path traversal 型の ID、未知 DB 内部版を拒否する。

## PR #3 の CI heartbeat 修正（2026-10-04）

対象は `.worktrees/integ`、branch `m2-integration`、開始 HEAD `cc25b09e281f2758d551005e86b4de13e29b66fb`。開始時の worktree は clean。Darwin arm64 / Rust 1.95.0 の CPU sandbox で実行し、commit / stage / push、backlog、公開 schema、Cargo.lock、golden は変更していない。上記の履歴とは別の検証である。

supervisor が提示した GitHub Actions macos-latest（3-core）の失敗は、`worker_checks_saved_schema_semantics_features_and_input_hash` の record が、最後の heartbeat から3019 msで `JOB_INTERRUPTED` になったもの。worker.log は空だった。この CI 記録は supervisor 提供の証拠であり、本 worker が CI を実行した結果ではない。

### 原因と判断

- 全状態操作と heartbeat が同じ5秒の SQLite busy_timeout を使っていた。3秒の test lease より長く writer を待てるため、待機中の heartbeat を reader の `BEGIN IMMEDIATE` が追い越すと、正当な所有 worker を失効させうる。prune は同 transaction 内で directory 削除も行う。重い render / encode 自体はこの writer transaction の外で実行される。
- heartbeat thread は最初の書込みエラーで、ログなしに終了していた。reader / claim / prune の `recover` は PID の存在を確認せず、期限のみで queued / running を terminal にしていた。CPU のスケジューリング遅延も異常終了と区別できなかった。
- worker は state open / get の後に heartbeat thread を開始し、起動側は child PID を登録していなかった。queued worker の claim loop は別 thread の heartbeat と併用されるが、startup の遅延は heartbeat を開始する前に発生しうる。
- test の `rewrite_record` は SELECT と UPDATE が別 transaction だった。間の heartbeat / claim 更新を、古い全 record の再保存で失う race もあった。各 Fixture の state root は独立しており、並列 suite 間の直接の SQLite lock 競合ではない。

変更前の CPU stress では CI の自然発生 failure を再現しなかった。追加した決定的な state tests を変更前実装へ適用すると、writer を保持した heartbeat が500 ms以内に戻らず、生存中の所有 PID にも `Interrupted` を返した（4 passed / 2 failed、Cargo exit 101）。この二つの欠陥は再現できたが、元 CI の直接の引き金が CPU starvation、SQLite lock、metadata race、その他の worker 停止のどれだったかは、空のログだけでは特定できない。

Unix の期限判定に生存確認を追加する設計判断は [14 ジョブ](../architecture/14-jobs.md#中断と取り消し) に記録した。既存 ADR-0050 の本文は変更していない。

### 修正と回帰確認

- heartbeat connection は SQLite 操作前から `min(100 ms, heartbeat_interval, heartbeat_timeout / 4)` の busy 待機上限を適用する。`SQLITE_BUSY` / `SQLITE_LOCKED` を記録して次の間隔で再試行し、他のエラーは記録して終了する。
- 起動と PID 登録を同じ短い writer transaction 内で行い、reader が child 起動済み・PID 未登録の窓を観測しないようにした。期限を超えても `kill(pid, 0)` が成功、または `EPERM` なら queued / running を維持する。terminal の復活、成果物の成功補正、暗黙再開は追加せず、publish fence は維持した。
- 起動 PID / epoch 時刻、heartbeat 開始・失敗・復帰、thread panic を worker.log に記録する。Fixture の terminal 判定に加え、待機 timeout でも同ログを表示する。
- `rewrite_record` を `BEGIN IMMEDIATE` で囲み、全 record の lost update を防ぐ。CLI の通常 lease は50 / 30000 ms、SIGKILL test だけ50 / 1000 msとする。Fixture の完了待機上限は負荷を考慮して60秒（旧20秒）。production の1000 / 30000 ms、MCP の50 / 1000 msは変更していない。

| 追加 / 維持した test | 確認 |
|---|---|
| `heartbeat_lock_wait_is_bounded_and_can_be_retried` | writer を保持中に heartbeat が500 ms以内に DatabaseBusy を返し、解放後の heartbeat と running 読取りが成功 |
| `expired_heartbeat_of_live_owner_preserves_queued_and_running_leases` | live owner の heartbeat を60秒前にしても get / list / prune / claim が slot を維持 |
| `spawn_registers_owner_before_worker_initialization` | heartbeat を開始しない遅延 executable でも、spawn 直後の PID 登録と stale queued の維持を確認 |
| `worker_heartbeat_retries_writer_contention_and_logs_recovery` | 実 worker の heartbeat が writer 競合をログに出し、writer 解放後に復帰ログと succeeded を確認 |
| `suspended_live_worker_is_not_interrupted_by_an_expired_heartbeat` | 実 worker を SIGSTOP、heartbeat を60秒前に変更して running を維持。SIGCONT / gate 解放後に成功 |
| `sigkill_is_detected_by_heartbeat_and_releases_slot` | 実 SIGKILL と1秒 leaseで Interrupted / JOB_INTERRUPTED、後続 queued の成功を維持 |
| `stale_lease_cannot_publish_or_become_successful_again` | owner のない expired record の中断と、publish / finish_error / claim による terminal 復活拒否を維持 |
