## 再現手順

注入された共有 `CARGO_HOME` / `CARGO_TARGET_DIR` と管理された `TMPDIR` を使う。今回の Cargo target は `27165a00ad87fa622bbc09e66789ccfd34399321ea5e5aa98154570e2210bf2c`、scratch は `worker_e7f149dac9d441d086451009252206c5`。各 process test / SDK は独立した temporary Project / job state を利用する。workspace / FFI tests の global job query には writable scratch の state root を明示する。

```sh
export CARGO_BUILD_JOBS=3
export KRONELLO_STATE_ROOT="$TMPDIR/mcp-workspace-state"
python3 scripts/fetch_fixtures.py
python3 scripts/fixtures.py generate
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --exclude kronello-gpu --exclude kronello-framebridge --locked -- --skip gpu_
python3 scripts/generate_swift_api.py --check

# SDK は製品依存に加えず scratch venv にだけ導入する
python3 -m venv "$TMPDIR/mcp-sdk-venv"
"$TMPDIR/mcp-sdk-venv/bin/pip" install -r scripts/mcp-client-requirements.txt
"$TMPDIR/mcp-sdk-venv/bin/python" scripts/mcp_client_check.py \
  --binary "$CARGO_TARGET_DIR/debug/kronello-mcp"
```

official Python SDK は **mcp==1.26.0**。script は package version と `types.LATEST_PROTOCOL_VERSION == "2025-11-25"` を実行時に検査する。requirements は今回の venv（Python 3.14）で利用した transitive packages も版固定する。最初の導入では `pip install mcp==1.26.0` を実行し、`pip freeze` の固定一覧を保存した。`-r` による別 venv への fresh install は今回未実行。

SDK script は実 `kronello-mcp` binary を起動する。stdio は official `stdio_client`、HTTP は official `streamable_http_client` と `ClientSession`、取消は official transport / JSON-RPC 型 / notification 型を使用し、SDK private request counter に依存しない。HTTP の認証 / 不正入力は同じ環境の `httpx` でも検査する。temporary bearer credential を test process のみに渡し、remote bind の無認証拒否も実 process で確認する。すべて明示 `cpu-reference`。render.submit の返却時に queued / running と成果物未確定を確認してから接続を閉じ、新接続で succeeded まで確認する。

## 失敗と修正・環境準備

- 最初の MCP suite は10 passed / 1 failed。既存 `public_api_fixture_commands_return_schema_valid_success_from_real_binary` の template preview が必要とする Noto fixture がなかった。`fetch_fixtures.py` 後の最終 stdio suite は11 passed。テストや診断を弱めていない。
- 最初の Clippy は新 dispatcher の `collapsible_match` により exit101。match guard へ整理し、最終 workspace Clippy は成功。
- 一時的に既存 project.info / export をすべて read_snapshot に変えた CPU workspace run は CLI 16 passed / 2 failed。ForceSafe の lock と sidecar cleanup の既存契約を変えていた。supervisor と合意した read-only inspection policy に限定し、通常 CLI / tool path を元の open/close へ戻した。その後の CLI machine suite は18 passed / 1 filtered。
- state root 未指定の workspace run は FFI boundary 7 passed / 1 failed、exact diagnostic も0 passed / 1 failed。失敗は job.list response の error / success assertion。既存 subscription は実ユーザーの default job state を使うため sandbox の writable roots 外を対象とすることが source から分かり、scratch state root を注入した exact test は成功した。元の error code / message 自体は test が表示しておらず、原因はこの環境差からの推定。同設定の workspace run へ継続した。FFI source / test は変更していない。
- 次の workspace run は media 5 passed / 2 failed。generated CFR / VFR / B-frame / HDR fixture がなかった。公式 `fixtures.py generate` の9素材生成・decode確認後に同じ workspace command を再実行した。これは GPU / codec fallback ではなく test input の準備である。
- 最終レビューで Origin を UTF-8 / 単一 header として parse する前に存在検査へ変え、malformed / duplicate Origin も403に統一した。追加した duplicate Origin assertion を含む4 unit tests と workspace Clippy は成功。最終 source の MCP binary を no-run build し、SDK check を再実行した。
