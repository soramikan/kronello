# JOB-002: Windows worker と各 OS の実プロセス検証

実装の決定は [ADR-0074](../adr/0074-windows-job-workers-and-process-evidence.md)。
Windows/Linux は CI 実行待ち。Windows の確認対象は jobs/platform のみで、full CLI/MCP は
media C loader（dlfcn.h / Unix loading / pkg-config headers）の移植待ちで build・render を保証しない。
macOS/Linux の CLI/MCP は明示 CPU reference を使う。GPU / hardware codec はこの検証に含めない。

## 高負荷 timeout の原因と再現

supervisor は既存 macOS worker PID 57005 を27分後に sample した。Running / completed_frames=0 のまま、
main と heartbeat が次の frame で同時に停止していた。提供 sample を読んで引用を保存し、raw sample file は worktree から削除済み。

```text
main: render_fixed_job -> JobStore::checkpoint -> JobStore::update
  -> drop(rusqlite::Connection) -> sqlite3_close -> sqlite3WalClose
  -> unixLock -> unixIsSharingShmNode -> unixEnterMutex -> mutex wait
heartbeat: worker_entry -> JobStore::heartbeat -> connect_with_timeout
  -> Connection::open -> sqlite3PagerOpen -> unixOpen
  -> findReusableFd -> sqlite3_mutex_enter -> mutex wait
```

これは bundled libsqlite3-sys 0.36.0 / rusqlite 0.38.0 / SQLite 3.51.1 の
global Unix VFS mutex と per-inode mutex の順序逆転である。`busy_timeout` を増やしても mutex wait は
SQLITE_BUSY を返さない。supervisor の sample は既存 binary の測定で、未コミット変更の acceptance result ではない。
[SQLite 3.51.2 release notes](https://www.sqlite.org/releaselog/3_51_2.html) に該当する broken-posix-lock detection の deadlock 修正がある。
この変更は workspace 全体の依存更新をせず、JobStore の Connection の open / SQL / close を
process-local gate に収めて順序逆転を防ぐ。Connection の Drop 完了後に gate を解放する。

worker の heartbeat は独立 watchdog と最後の成功時刻を monotonic clock で共有する。
heartbeat_timeout を超えた場合は log に期限超過を記録して process を終了し、reader が interrupted とする。
heartbeat thread の join 中も監視する。whole-process SIGSTOP / scheduler 停止中の watchdog 実行は保証しない。

この worker は raw SQLite への診断用 `raw-stress` entry も持つ（test-worker feature のみ、公開 CLI/MCP にはない）。
初回診断 driver の同一 process・2 thread・各1000 open/update/close は、1回目が exit 0 / 0.52秒、
2回目が30秒で timeout / SIGKILL exit -9 となった。外側 Python driver が child を kill + wait した。
この timeout 自体から同一 stack を再測定したとは主張せず、stack の根拠は supervisor の sample とする。
logs / commands / exits は `target/job-002-raw-stress/results.json` / `raw-*.log`。
最終版の診断entryは JSON 内 completed_frames を更新し、FULL synchronous を設定する。
`--output target/job-002-raw-current --raw-stress` の3試行はすべて exit 0（1.153 / 1.399 / 1.038秒）。
この変更後の3試行で再び deadlock したとは主張せず、初回のtimeoutとsupervisor sampleを分けて保存する。

別の再現では6秒のwriter lockにより、旧 checkpoint が5秒で JOB_STORAGE_ERRORを返した。
slot claim と checkpoint は短い busy 待機で SQLITE_BUSY / SQLITE_LOCKED / JOB_PROCESS_BUSY のみを再試行する。
status polling は WAL read、stale/dead active record の場合だけ writer を取得して recovery を再確認する。
heartbeat retryのみの中間版では実 Sequence jobの60秒Queued timeoutとRunning stallを再現した。
この中間版の失敗を最終版の成功として扱わない。

## 再現可能なコマンドと CI

```sh
python3 scripts/fetch_fixtures.py
python3 scripts/fixtures.py generate
python3 scripts/job_evidence.py --check-lints
python3 scripts/job_evidence.py --output target/job-002-evidence
# CPU load を作り、2つの実 CLI job suite を各32 test threadsで並行実行
python3 scripts/job_evidence.py --output target/job-002-stress --stress --cpu-hogs 64 --warmup-seconds 90
# 旧 open/close を gate なしで再現する診断。30秒で kill/wait、最大3試行。
# affected SQLite では timeout による非ゼロ exit を期待し、通常 CI には含めない。
python3 scripts/job_evidence.py --output target/job-002-raw --raw-stress
```

evidence runner は全 command の stdout/stderr log、exit、OS/version、Rust verbose version、HEAD / dirty status、
load sample、worker registry、final cleanup を保存する。load平均50への到達は artifact の実測で判断し、
64 burner processを起動したことだけで到達済みとは扱わない。burner / timed-out commandは finally で終了・waitする。
test workers の registryは1行をserializeして1回のappend writeで保存し、並行writerのJSON断片混入を避ける。
外側cleanupは登録PIDの実commandとjob UUIDを照合してからkillし、再利用PIDの別processを殺さない。
残存workerを見つけたrunは回収できても失敗。uninspectable PID / registry破損も失敗で、後続の回収を続ける。
Linux の外側 Python runner も subreaper となり、強制終了した harness の孫 worker を adopt / waitpid する。
Python `test_linux_cleanup_reaps_worker_after_harness_is_killed` は Linux CI 専用で、macOSでは skip と記録する。

`.github/workflows/ci.yml` は Windows / Linux / macOS で runner を明示実行し、
`job-002-<OS>-<arch>` artifactを `always()` でuploadする。先行テストが失敗しても evidence stepを実行する。
WindowsはMSVCのjobs/platformのみ、Linux/macOSはCLI jobs全件とMCP EOF試験も実行。
workflow_dispatchを追加した。Windows/LinuxのCI run URL・revision・artifact・exitはsupervisorのpush後に確認する。

## macOS 実行結果

基点 HEAD `d00219e950b0c9be28a777eb5d6f2960995c9fcb` + この worktree の未コミット変更。
環境は macOS 27.0 / arm64、Rust 1.95.0、bundled SQLite 3.51.1。

connection gate / watchdog後の `python3 scripts/job_evidence.py --output target/job-002-macos-fixed --stress`
は exit 0。jobs processes 6 passed / 1 ignored、state 7 passed、CLI 23 passed、MCP EOF 1 passed、
並行CLI suiteは23/23・23/23 passed（13.88秒 / 13.82秒）。最終cleanupは133 worker登録、残存0、errors0。
これは通常負荷の記録で、load ~50の証明とは分ける。

`python3 scripts/job_evidence.py --output target/job-002-macos-high-load --stress --cpu-hogs 64 --warmup-seconds 90`
も exit 0。jobs processes 7 passed / 1 ignored（2 slots / queued killを含む）、state 7 passed、CLI 23 passed、
MCP EOF 1 passed、feature-enabled jobs/platform clippyも exit 0。
並行CLI suiteは23/23・23/23 passed（libtest 34.87秒 / 37.31秒、command全体38.624秒 / 37.255秒）。
一分load平均の全sample範囲は24.84–165.47、並行suite終了までの最後40 sampleは136.98–165.47で、目標~50を超えた。
138 worker登録、残存0、cleanup errors0、`cleanup.no_orphans=true`。このrunが起動・登録したworkerの証跡であり、
supervisorが回収中の過去runのhost全processを調査した結果ではない。burner64 processもfinallyでkill/waitした。
その後、publication raceを2 slots・両staging準備後の同時解放に強化した processes suiteも7 passed / 1 ignored。

最終 `python3 scripts/job_evidence.py --output target/job-002-macos-final` は exit 0。
強化したpublication race / 個別duplicate worker guard / submit応答検証前のPID捕捉を含み、
jobs processes 7 passed / 1 ignored、state 7 passed、CLI 23 passed、MCP EOF 1 passed。
Python cleanup試験2 passed / Linux-only 1 skipped、feature-enabled clippyも exit 0。
60登録workerの残存0 / cleanup errors0。`target/job-002-macos-final/evidence.json` がOS/version/command/exitの記録。

workspace clippy（all-targets / locked / -D warnings）は exit 0。
`cargo check --target x86_64-pc-windows-msvc -p kronello-jobs -p kronello-cli --locked` は target installedだが exit 101、
bundled SQLite C buildのWindows標準headersがなく `stdlib.h not found`。full Windows CLI buildの証拠にしない。
`cargo check -p kronello-platform --all-targets --features test-support --target x86_64-pc-windows-msvc --locked` は exit 0。
初回workspace CPU testはFFI job.listの既定user state areaがsandboxで書けず失敗した。
再実行は `KRONELLO_STATE_ROOT` をmanaged TMPDIR内に指定した。
`KRONELLO_STATE_ROOT="$TMPDIR/kronello-workspace-state" CARGO_BUILD_JOBS=3 cargo test --workspace --exclude kronello-gpu --exclude kronello-framebridge --locked -- --skip gpu_`
は exit 0、88 suite合計578 passed / 0 failed / 1 ignored / 10 filtered。logは `target/job-002-workspace.log`。
`cargo fmt --all --check` は exit 0、`python3 -m unittest scripts.tests.test_job_evidence -v` は2 passed / Linux-only 1 skipped。

## 残件

- Windows/Linuxの実CI、Windows media native port、macOS/Windows第二volume。
- PID identityのDB保存、whole-process hang/停止と進捗監視、SIGKILL/watchdogが残すstagingの回収・電源断後照合はRECOVERY-001。
- 全workspaceのSQLite更新は別の依存更新として検討する。依存のライセンスは引き続きMIT / SQLite public domain。
